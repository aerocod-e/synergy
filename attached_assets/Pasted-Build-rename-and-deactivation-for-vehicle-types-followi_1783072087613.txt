Build rename and deactivation for vehicle types, following the same soft delete pattern already used everywhere else in this app. Follow all steps in order.
Step 1, backend: allow renaming a vehicle type
Open the existing updateVehicleType function used by PATCH /api/vehicle-types/:id. Confirm it already accepts loadingFee and unloadingFee. Add support for an optional name field in the same request. If name is provided, update it, validate it is a non empty string, and validate it does not collide with another active vehicle type's name, using the existing unique constraint already in place. No restriction based on whether the type has already been used by vehicles or trips, renaming must always be allowed regardless of history.
Step 2, backend: count how many vehicles use a given type
Add a new endpoint, GET /api/vehicle-types/:id/vehicle-count, Super Admin only, returns the count of vehicles currently active (is_active = true, deleted_at IS NULL) referencing that vehicle_type_id. This powers the warning shown before deactivation.
Step 3, backend: deactivate a vehicle type, always allowed, no blocking
Add a new endpoint, PATCH /api/vehicle-types/:id/active, Super Admin only, accepts { isActive: boolean }. Sets vehicle_types.is_active to the given value. This must never be blocked by anything, no check against vehicle count here, deactivation must always succeed immediately when called. This also supports reactivating a previously deactivated type by passing isActive: true, matching the same reactivation pattern already used for stakeholders elsewhere in this app.
Step 4, backend: block trip creation using an inactive vehicle type
Open tripController.ts, find createTrip. After looking up the vehicle's vehicle_type_id, also check whether that vehicle type's is_active is currently true. If the vehicle type exists but is_active = false, return 422 with a message clearly directed at the Trip Admin, for example "This vehicle's type is no longer active. Please reassign this vehicle to a different vehicle type before creating a trip." This check must happen before any fee calculation logic runs.
Step 5, backend: confirm past and current trip history is fully unaffected
Do not change anything in trip_fees, wallet_ledger, or any historical read path. Confirm explicitly, by reading the code, that trip detail retrieval, the public lookup, and the audit report endpoints all read fee amounts directly from trip_fees, which stores fully resolved numeric amounts at the time of trip creation, and never re-joins live to vehicle_types.is_active to decide whether to display those amounts. Report this confirmation clearly. If any of these read paths does filter or hide data based on the vehicle type's current active status, flag it as a bug to fix, since historical trips must always display correctly regardless of whether their vehicle type is still active today.
Step 6, frontend: rename and deactivate on the Super Admin Config screen
Open artifacts/mobile/app/(superadmin)/config.tsx. On each vehicle type card, alongside the existing edit pencil icon that already opens the unified rate edit modal, add the vehicle type name itself as an editable field inside that same modal, so renaming happens through the same edit flow already in place rather than a separate button.
