Fix two related navigation bugs found during investigation. Do not change anything else.

Fix 1, the routing collision

Six top level route groups, (profile), (stakeholder), (stateadmin), (superadmin), (tripadmin), (tabs), all currently resolve to the exact same root path, /, because Expo Router strips group name parentheses when generating routes, and each group's own index screen claims that same bare path. On any cold app start or full reload, the router cannot tell these apart and deterministically picks (profile), the alphabetically first candidate, regardless of the logged in user's actual role.

Fix this at the source, not by working around the symptom. Confirm whether app/_layout.tsx or a similar root entry point already has explicit logic intended to redirect a logged in user to their correct role group, and if so, why that logic is not currently preventing this, since the investigation found it treats (profile) as an always-allowed exception and therefore never corrects an already-wrong resolution landing there.

The correct fix is to remove the ambiguity itself, not add another special case. Ensure the true landing route, the bare root path with no group, has exactly one unambiguous owner, most likely a single dedicated entry redirect screen, or ensure app/_layout.tsx's initial redirect logic runs before the router settles on any group's index screen, actively sending a freshly restored session straight to that user's correct role group every time, rather than only correcting a mismatch after the fact. Confirm your chosen approach does not reintroduce the same ambiguity for unauthenticated users landing on (public) or (auth).

Fix 2, the back button

In app/(profile)/index.tsx, the back button currently calls router.back() unconditionally. Change this to check router.canGoBack() first. If true, call router.back() as it already does. If false, meaning there is nothing to go back to, navigate explicitly to that user's correct role home screen instead of doing nothing or throwing a navigation warning.
